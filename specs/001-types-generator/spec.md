# Feature Specification: Types and Generator (foundations, part 1)

**Feature Branch**: `001-types-generator`

**Created**: 2026-10-31

**Status**: Draft

**Input**: User description: "Spec 001, foundations part 1: types and generator. Implements SRD §3
(data requirements), §6 (architecture) and the P0 pipeline gate's first check (SRD §5). Carry
gitma's LinkML schema into gitma2 and generate Pydantic models, JSON Schema and a data dictionary;
a vectorised Python generator reproducing gitma generator 0.3.0 and 0.5.0 semantics from a 64-bit
seed, deterministic regardless of batch order or worker count, producing in-memory batches and
NDJSON + Float32-pack files with digests; conformance to gitma's committed scenario files; a
`tma2-generate` CLI mirroring gitma's; repository skeleton with CI and the site skeleton.
Out of scope (002): reference estimators, the physics layer, the ONNX harness, the rest of P0."

**SRD traceability**: SRD §3 (data requirements: generation, conformance, types, labels), §6
(architecture and tooling), §5 gate P0 check 1 (generator reproduces gitma's files), §2 (problem
variants CV and MAN). Constitution principles I (types), II (determinism), VI (portable artefact,
Python stack) and the Development Workflow.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Reproduce gitma's scenarios from Python (Priority: P1)

A researcher runs the gitma2 generator with the same seed, count and parameter ranges that gitma
used, and gets the same scenarios: the same ownship and target tracks, bearings, dropouts, zig
indices and manoeuvre spans, so that every later comparison with gitma's baselines and results is
on identical data.

**Why this priority**: It is the P0 gate's first check and the premise of the whole project: the
oracle-ceiling measurement, the frozen IMM reference and gitma's committed results are only
usable if the data is the same.

**Independent Test**: Generate the fixture seeds with gitma2 and compare, record by record, with
the committed gitma files; the test passes only when every integer, flag and string is identical
and every float is equal after float32 rounding (any residual within one float32 ulp is listed
in the test output and counted).

**Acceptance Scenarios**:

1. **Given** gitma's committed ten-scenario golden file (seed 1, test split) and its parameter
   ranges, **When** gitma2 generates seed 1, count 10, test split with the same ranges,
   **Then** the output is record-for-record equal under the conformance rule.
2. **Given** a manoeuvring-target fixture generated by gitma at a pinned commit (seed 777,
   phase-4 ranges, 50 scenarios per split) and committed to gitma2, **When** gitma2 generates the
   same seed and ranges, **Then** every scenario, including its manoeuvre spans, kinds, speed
   changes and redraw count, is equal under the conformance rule.
3. **Given** a constant-velocity fixture (phase-4 generator code with iteration-4 ranges, which
   contain no target-manoeuvre parameters), **When** gitma2 generates it, **Then** it is equal
   under the conformance rule and every scenario's manoeuvre list is empty.
4. **Given** the same seed and ranges, **When** generation is run with a different batch size, a
   different number of workers, or scenario by scenario, **Then** the output is byte-identical.

### User Story 2 - One schema, generated types, readable files (Priority: P1)

A developer changes or reads a data type (scenario, track, observation, dataset header, manoeuvre
span) in exactly one place, the LinkML schema, and gets Python models, JSON Schema and the data
dictionary page from it; gitma's files validate against the generated models unchanged.

**Why this priority**: Constitution principle I is non-negotiable, and keeping gitma's files
readable is what lets spec 002 check the reference estimators against gitma's predictions.

**Independent Test**: Edit a slot description in the schema without regenerating; CI fails with a
staleness message. Regenerate; CI passes. Load each committed gitma fixture through the generated
validators; all pass.

**Acceptance Scenarios**:

1. **Given** the carried-over schema, **When** the generation step runs, **Then** Python models,
   JSON Schema and a data dictionary page are produced and committed, and a check compares them
   with a fresh generation.
2. **Given** a gitma scenario file at schema 0.16.0, **When** it is read with the generated
   validators, **Then** every record validates and round-trips to identical canonical JSON.
3. **Given** a file whose header names an unsupported schema or generator version, **When** it is
   read, **Then** it is rejected with a message naming both versions.

---

### User Story 3 - Generate datasets from the command line (Priority: P2)

A researcher creates a dataset for evaluation with one command that mirrors gitma's generator
options, gets the four splits as inspectable and compact files with content digests, and a header
that records exactly how the files were made.

**Why this priority**: Evaluation splits must exist as files with digests (constitution II); the
CLI is how every later spec pins its data.

**Independent Test**: Run the command on a clean checkout; the four split files exist in both
formats, each header carries the generator commit, clean flag, schema and generator versions, the
ranges digests and the split bounds; the digest file matches the files; a second run gives
byte-identical files.

**Acceptance Scenarios**:

1. **Given** a seed, count, ranges file and output directory, **When** the command runs,
   **Then** train/validation/test/held-out splits are written in the line-per-scenario format and
   the compact binary format, with a digests file, at a rate of at least 1,000 scenarios per
   second on a 4-core runner.
2. **Given** a dirty working tree, **When** the command runs without the override flag,
   **Then** it refuses; with the flag it proceeds and records the dirty state in every header.
3. **Given** the noise-free option, **When** the command runs, **Then** bearings carry no noise
   and no dropouts and the header says so.

---

### User Story 4 - Fresh batches for training without files (Priority: P2)

A training process asks the generator for batch *k* of a seeded stream and gets the same batch
every time, with the per-scenario labels training needs (truth tracks, manoeuvre spans and kinds
per timestep, zig and manoeuvre indices), without writing anything to disk.

**Why this priority**: On-the-fly generation is how gitma2 avoids gitma's multi-gigabyte feature
files on free runners (SRD §3, §4).

**Independent Test**: Request batches 0..9 of seed S in order, then in reverse, then from two
processes; the arrays are identical. Request batch 3 alone; it equals batch 3 from the sequence.

**Acceptance Scenarios**:

1. **Given** a seed and a batch index, **When** a batch is requested, **Then** its scenario
   indices are a fixed function of (seed, batch index, batch size), and each scenario is the one
   the file-writing path would produce at that index.
2. **Given** a batch of 256 scenarios of up to 360 timesteps, **When** it is produced on a 4-core
   runner, **Then** it takes under 0.5 s, so generation is not the training bottleneck.

---

### User Story 5 - A reviewable, checked repository (Priority: P3)

A contributor or agent opens a PR and gets automatic lint, type, test and schema-staleness checks,
and the public site builds with the data dictionary and glossary pages, so the project's working
rules are enforced from the first PR.

**Why this priority**: Required by the constitution's Development Workflow; cheap to add now,
expensive to retrofit.

**Independent Test**: Open a PR with a type error, a lint error and a stale generated file; three
checks fail. Fix them; all pass and the site builds.

**Acceptance Scenarios**:

1. **Given** a PR, **When** CI runs, **Then** lint, static types, unit and golden tests, schema
   staleness and the site build each report separately.
2. **Given** the schema, **When** the site builds, **Then** the data dictionary page lists every
   class and slot with descriptions and units, and the glossary page exists with the project's
   core terms.

### Edge Cases

- A ranges file that lacks target-manoeuvre parameters (constant-velocity data) must be accepted
  and yield empty manoeuvre lists, not an error.
- A ranges file that has target manoeuvres but no held-out ranges must be refused, as gitma does.
- Scenarios that gitma redraws (geometry closer than the minimum range, second zigs or manoeuvres
  that do not fit) must be redrawn in the same order from the same streams, so redraw counts match.
- A seed given as a decimal string beyond 2^53 must be parsed exactly (64-bit), not through a
  double.
- Negative zero in stored floats must be written as positive zero.
- A float that differs from gitma's by exactly one ulp after float32 rounding is a reported
  residual, not a failure; two ulps is a failure.
- Interrupting a file write must not leave a file that validates: write to a temporary name and
  rename.

## Requirements *(mandatory)*

### Functional Requirements

**Types**

- **FR-001**: The project MUST carry gitma's LinkML schema (version 0.16.0) unchanged in content,
  bumping only if a slot is added, and MUST generate from it the Python models, JSON Schema and
  the data dictionary page; hand-written equivalents are forbidden.
- **FR-002**: CI MUST fail when the committed generated output differs from a fresh generation.
- **FR-003**: Every file read at runtime MUST be validated with the generated models; the header's
  schema and generator versions MUST be checked and mismatches rejected with both versions named.
- **FR-004**: Records MUST be written as canonical JSON (sorted keys) and MUST round-trip through
  the models to identical text.

**Generator**

- **FR-005**: The generator MUST implement gitma's generator 0.5.0 algorithm (rate-limited ownship
  zigs with the across-line-of-sight rule and second zig, 0–3 target course changes drawn once per
  scenario, one speed change in a declared fraction, redraw rules, minimum-range check) and MUST
  produce constant-velocity data when the ranges file carries no target-manoeuvre parameters.
- **FR-006**: Randomness MUST come from gitma's scheme: a SplitMix64 derivation of a per-scenario
  seed from the dataset seed and scenario index, and gitma's stream generator and stream layout
  per scenario, so that any seed produces the same scenario in both repositories.
- **FR-007**: Output MUST be identical regardless of batch size, worker count or evaluation order;
  a scenario depends only on (dataset seed, index, ranges, noise-free flag).
- **FR-008**: Stored floats MUST be float32-rounded with negative zero mapped to positive zero.
- **FR-009**: The generator MUST produce, per scenario, ownship and target truth tracks, bearings
  with validity flags, and the metadata gitma records (seed, index, parameters, samples, zig and
  turn indices, second-zig indices, manoeuvre spans with kinds, manoeuvre start and end indices,
  zig time, mean and minimum range).
- **FR-010**: The generator MUST expose an in-memory batch interface returning fixed-shape arrays
  (padded to the window maximum for the ranges, with masks) and per-timestep labels (true state,
  manoeuvre-in-progress flag, kind of the last manoeuvre, time since zig and since last manoeuvre
  end).
- **FR-011**: The generator MUST sustain at least 1,000 scenarios per second for file output and
  at least 500 scenarios per second per batch for in-memory output on a 4-core GitHub runner.

**Conformance and golden files**

- **FR-012**: The repository MUST commit conformance fixtures: gitma's `seed1-count10-test.ndjson`
  with its ranges; a manoeuvring fixture (seed 777, phase-4 ranges, 50 scenarios per split) and a
  constant-velocity fixture (seed 777, iteration-4 ranges, 50 per split), both generated by gitma
  at a pinned commit recorded beside them.
- **FR-013**: A conformance test MUST compare gitma2's output with each fixture: integers, flags
  and strings byte-equal; floats equal after float32 rounding; any residual within one float32 ulp
  reported with its field and count; anything larger fails.
- **FR-014**: Each package MUST have a golden-file test (fixed seed in, byte-identical output out)
  whose expected files are regenerated only deliberately, with the reason stated in the PR.

**CLI and files**

- **FR-015**: A `tma2-generate` command MUST accept seed, count, output directory, ranges file,
  held-out ranges file, noise-free, allow-dirty and format options with gitma's semantics, and
  MUST write train/validation/test (80/10/10 by index) and held-out splits.
- **FR-016**: Files MUST be written in the line-per-scenario JSON format and the Float32-pack
  format gitma defines, each with a header first record, plus a digests file; the two formats MUST
  round-trip losslessly.
- **FR-017**: Headers MUST record the generating commit, a dirty flag, schema and generator
  versions, the command line with ranges digests, the dataset seed, split and index bounds,
  scenario count and redraw count; the command MUST refuse a dirty tree without the override.
- **FR-018**: File writes MUST be atomic (temporary name, then rename).

**Repository and site**

- **FR-019**: The repository MUST be a `uv`-managed Python project with the source under one
  package, lint, strict static typing, tests, and a CI workflow on the free 4-core runner that
  runs lint, typing, tests, schema staleness and the site build as separate checks.
- **FR-020**: The site MUST build with a welcome page, the generated data dictionary page and a
  glossary page carrying gitma's terms plus gitma2's (physics layer, oracle ceiling, efficiency,
  steady leg, settled row).
- **FR-021**: The generator and its helpers MUST be plain functions over arrays with no hidden
  state (constitution III, portability of `sim`).

### Key Entities

- **Scenario**: one ownship-versus-target run: metadata (seed, index, parameter draws, indices,
  manoeuvre spans), ownship track, target track, observations. As gitma schema 0.16.0.
- **ParameterRanges**: the per-dataset sampling ranges (window, speeds, zig rule and angles, range
  distribution, noise σ values, dropout fraction, turn rates, target-manoeuvre settings); its
  content digest is part of the header.
- **DatasetHeader**: first record of every file: versions, seed, split, bounds, counts, provenance.
- **ManoeuvreSpan**: start index, end index and kind (course or speed) of one target manoeuvre.
- **Batch**: fixed-shape arrays for N scenarios (inputs, masks, truth and per-timestep labels)
  plus the scenario indices, a function of (seed, batch index, batch size, ranges).
- **Conformance fixture**: a gitma-generated file set with its ranges, commit and digests.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: All three conformance fixtures (gitma golden seed 1; seed 777 manoeuvring; seed 777
  constant-velocity) pass the conformance rule with zero failures and the ulp-residual count
  reported in the test output.
- **SC-002**: Generation of the same seed with batch sizes 1, 64 and 1,024 and with 1 and 4
  workers produces byte-identical files.
- **SC-003**: File generation runs at ≥ 1,000 scenarios per second and a 256-scenario batch is
  produced in under 0.5 s on the CI runner, measured and printed by a test.
- **SC-004**: Every gitma scenario file in the fixtures validates against the generated models and
  round-trips to identical canonical text.
- **SC-005**: A PR with an introduced lint error, type error and stale generated file fails
  exactly those three checks.
- **SC-006**: The site builds in CI with the data dictionary listing every class and slot of the
  schema and a glossary with at least the terms named in FR-020.

## Assumptions

- gitma at commit `d0aec60` is the reference implementation; its generator code at that commit
  defines "0.5.0 semantics", and its iteration-4 ranges define the constant-velocity variant.
  Reproducing older generator versions (0.2.0, 0.3.0 code) is not required; the constant-velocity
  problem is produced by the current code with manoeuvre-free ranges.
- Conformance fixtures are small (10 and 50 scenarios per split) so the repository stays light;
  the P0 gate in spec 002 may add a larger one-off comparison.
- Float residuals of one ulp are tolerated because transcendental functions differ by platform
  (constitution III); they are reported so that any drift is visible.
- The split rule is gitma's: 80/10/10 by index within the count, and the held-out split uses the
  held-out ranges with the same count as the test split.
- The site is Docusaurus as gitma's, with the data dictionary generated at build time from the
  schema; blog and algorithm notes start empty.
- Foundations are split into 001 (this spec) and 002 (reference estimators, physics layer, ONNX
  harness, P0) so that each PR has one hard acceptance test. This is an agent decision under
  `AGENTS.md` (Autonomy); the alternative, one spec, was not taken because the conformance test
  is a natural stopping point and the physics layer depends on nothing in it but the batch
  interface.
- No owner-only item (spending, scope, classification, gate criteria, deletion, publishing) is
  touched by this spec.
